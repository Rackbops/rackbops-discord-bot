### What the data says (read from source, not guessed)

- `routingData` (from #245's `loadRouting`) is `{ routing, discovery }`, both nullable. `routing.plugins[name].servers[guildId] = { commands: "all" | string[], postTo? }`; `routing.webhooks[channelId] = { id, guildId, addedAt, addedBy, broken? }` (`broken` is Discord's reason once it refused — the bot sets it when a post fails; adding a webhook for that channel again replaces it and clears `broken`: `applyRoutingRequest`'s `webhook-add`, "One webhook per channel"); `routing.results` is the last 20 `{ id, action, plugin?, channelId?, ok, reason?, at }`, oldest first — a `webhook-add` result carries `channelId`, the channel Discord said the webhook posts to. `discovery = { generatedAt, bot: { id, username }, inviteUrl, homeGuildId, guilds: [{ id, name, channels: [{ id, name, canSend }], commands: { registered, error?, at } | null }], plugins: { [name]: { posts, commands } } }`.
- **A server card's states come from `discovery.guilds[].commands`** (the planning note on the issue): `{ registered, at }` → live; `{ error }` → Discord refused (usually 50001, invited without `applications.commands`) — the fix is the invite link **and then a retry**, since re-authorising a bot that is still a member emits no event (#259); `null` → never registered there: single mode and not the home server (normal), or a server that arrived during a gateway re-identify (#259) — a retry cures it. **"Try again" needs no new bot action**: re-sending any placed plugin's *current* routing as a `routing-set` re-runs `applyRouting` for every server. When no plugin is placed at all there is nothing to re-send and the only retry is a restart — say so instead of offering a button that cannot work.
- **Routed mode** = `routing.plugins` has at least one entry. In single mode every server but the home one has `commands: null` by design — not a problem.
- `discovery.plugins` holds loaded plugins only; a plugin with no `routing.plugins` entry is **unplaced** and lives in the home server (`homeGuildId`, ADR-0006 decision 3); a home server not among `guilds` means every unplaced plugin is registered nowhere (#260's warning).
- The Config editor: `renderEnvFields()` builds one control per key of `loadedEnv` through `buildEnvControl(key, value)`, which consults `FIELD_META[key]` (`control: "tags" | "select" | "branch"`, `options`, `hint`, `placeholder`) and ends with the common tail `control.id = "env-" + key; control.dataset.key = key;`. The `select` branch already "represents an out-of-enum stored value faithfully as its own option" and offers `""` as `— default —`. The bar's collector reads `#env-fields [data-key]` and `planEnvSave` diffs values — a `<select>` with `data-key` is read exactly like an `<input>`. `FIELD_META.DISCORD_SERVER_ID.hint` is the stale "Which Discord server slash commands register to…" (false in routed mode since #239). `bot-ops.sh`'s whitelist patterns for the three keys are `^[0-9]{5,25}$`; `src/config.ts` reads `ANNOUNCE_CHANNEL_ID` as required, the other two as optional (`RELEASE_ANNOUNCE_CHANNEL_ID` falls back to the announce channel; `DISCORD_SERVER_ID` unset means register globally).
- Tabs: `TAB_IDS = ["overview", "plugins", "settings"]` (the `TABS` lifted block), one `<nav><div role="tablist">` with three `rb-tabstrip__tab` buttons and three `rb-tabpanel adm-panel` panels; `showTab` looks tabs and panels up by id (`tab-<id>`, `panel-<id>`); `server.test.ts` pins "exactly one tablist, holding the three tabs", `panelOfIds()` (which section ids sit in which panel), the `expected fragments` counts (`class="rb-tabstrip__tab` 3, `class="rb-tabpanel adm-panel"` 3, `class="rb-card"` 6), the TABS_DOM harness ("three tab buttons, three panels"), and `tabFromHash` for the three names. All of these move to four.
- #245 left the pieces this reuses: `routingData`, `loadRouting()` → `refreshRoutingSteps()`, `routingStepModel` (per plugin), `ensureRouteState` (seeds from a ready model only, `st.seeded`), `sendRouting(plugin)` (the whole current selection, in-flight/held), `refreshDiscovery(plugin)` (per-plugin, its own poll), `ROUTING_POLL_MS`, `ROUTING_ANSWER_TIMEOUT_MS`, `api()`, `timeoutSignal`, `MUTATION_TIMEOUT_MS`, `setApplyText`, `openCards`, `cardHeaderEls`, `describeOutdatedBanner` (the banner stays).

### Decided — not open for re-planning

1. **A fourth tab, Servers, after Plugins.** `TAB_IDS = ["overview", "plugins", "servers", "settings"]`; `#tab-servers` / `#panel-servers` in the same markup shape; every pinned three becomes four. Its panel holds one static `<section id="servers-section" class="rb-card">` with an `<h2>Servers</h2>`, an intro line, a toolbar (*Refresh from Discord*, *Copy invite link*) and a `#servers-list` that `renderServers()` fills with one `section.rb-card.server` per server (dynamic, so the static `class="rb-card"` count only grows by the sections this plan adds statically).
2. **One card per server the bot is in** (`discovery.guilds`, in order), decided purely by `serverCardModel(guild, routingData, pluginsData)`: `{ id, name, home: boolean, commands: { state: "live" | "refused" | "unregistered" | "single-mode", registered?, at?, error? }, plugins: [{ name, scope: "all" | [channel names or ids], postsTo: channel name or null, webhook: "none" | "ok" | "broken", byDefault: boolean }], webhooks: [{ channelId, channelName | null, addedAt, addedBy, broken? }] }`. `plugins` lists every plugin whose routing entry names this guild, plus — on the home card only — every unplaced plugin as `byDefault: true` (*"lives here by default"*). `commands.state` is `single-mode` for a `null` outside routed mode (drawn as one quiet line, never a problem), `unregistered` for a `null` in routed mode. Below the last real card, **one card per server routing names but discovery does not** (from `routing.plugins[*].servers` keys and `routing.webhooks[*].guildId`): `route__row--off`-style, *"Server <id> — the bot is no longer in it"*, listing the placements and webhooks it still holds, with the #245 sentence that they are dropped the next time each plugin's placement changes.
3. **Card body, top to bottom:** the commands line (*"Commands live — <n> registered <local time>"* / *"Discord refused the commands here: <error>"* + a *Re-invite the bot* link (`discovery.inviteUrl`, only when it starts with `https://discord.com/`, `rel="noopener"`) + *Try again* / *"Commands were never registered here."* + *Try again* / the single-mode line *"No commands here: only the home server registers commands until a plugin is placed."*); **Plugins here** (one line each: *"music — anywhere · posts to #spotify (webhook)"*, *"wow — #general, #raids · posts as the bot"*, *"warbandeer — lives here by default"*); **Webhooks** (one row per webhook whose `guildId` is this server: *"#<channel>"* by name from `discovery` or *"channel <id> (no longer visible)"*, *"added <local date> by <addedBy>"*, *"stopped working: <broken>"* when set, and a *Remove* ghost button); **Add a webhook**: one `<input type="password" autocomplete="off" placeholder="Paste the webhook URL">` (a webhook URL is a credential: never shown, never logged, never stored) with an *Add* button and the hint *"The bot asks Discord which channel it posts to. If that channel already has a webhook, this one replaces it."*
4. **Add / Remove / Try again / Refresh all go through one poller.** A new `pollForResult(id, startedAt, opts)` (browser-only, beside `awaitRequestResult`): every `ROUTING_POLL_MS` re-read `GET /api/routing` (tolerating a failed read, clearing on `unauthorized`), stop when `routing.results` holds `id` or `ROUTING_ANSWER_TIMEOUT_MS` has passed; resolves `{ result }` or `{ timeout: true }`; the fresh `routingData` is stored on every successful read. **Add**: `POST /api/webhooks` with `{ url }` — the field is emptied **before** the request is awaited (its value never survives the click, whatever the outcome; a refusal means paste again), the card's status line (`role="status"`) reads *Adding…*; on `{ ok: true, id }` poll; `result.ok` → `refreshServers()` (the webhook now appears under `result.channelId`'s name); `result.ok === false` → *"The bot refused it: <reason>"* (the bot's reason never carries the URL); a non-200 POST → *"Couldn't send it: <text>"*; timeout → the 30 s sentence with *Check again* (one more poll window). **Remove**: `DELETE /api/webhooks/<channelId>` behind a `confirm("Remove the webhook for #<channel>? The bot posts there as itself afterwards.")`, then the same poll and refresh. **Try again**: `retryRegistration()` — the first plugin with a `routing.plugins` entry, in `pluginsData` order; `ensureRouteState(name, routingStepModel(name, routingData, Date.now()))` and `sendRouting(name)` (a no-op change: the saved placement is re-sent, the bot re-registers every server, #245's state machine shows *Applying…* on that plugin's card); when it settles, `refreshServers()`; when no plugin is placed, no button — the line says *"Nothing is placed yet, so there is nothing to re-send. Restart the bot (Overview) to retry."* **Refresh from Discord** (tab level): `POST /api/discovery/refresh`, poll, `loadRouting()`; the toolbar shows *Refreshing…* / the outcome, and *"Last read from Discord <local time>"* beside the button at all times (from `discovery.generatedAt`). **Copy invite link**: `navigator.clipboard.writeText(discovery.inviteUrl)` → *Copied*; when the clipboard API is unavailable or rejects, a read-only `rb-input` holding the URL appears, selected, so it can be copied by hand. All server-sourced text via `textContent`; the URL never goes through `innerHTML`.
5. **Needs attention lives on Overview, first, as `<section id="attention-section" class="rb-card">` above Status.** `needsAttention(input)` is pure: `input = { status, plugins, routingData, env, schema, labelOf }` → an array of `{ kind, text, fix: { label, go: "plugins-card:<name>" | "settings" | "servers" | "retry" | "restart" | "none" } }`, in this order, each kind at most once per subject: **`missing-setting`** — every `enabled` plugin with `missingEnv` (*"music needs Spotify client secret"*, labels via `labelOf`) → *Fill it in* opens the Plugins tab and that card (`openCards.add`, `showTab("plugins", false)`, then focus its header); a required core key that is blank in `env` (per `schema[key].required`) → *Set it* opens Settings; **`commands-refused`** — a guild with `commands.error` → *"<name>: Discord refused the bot's commands (<error>)"* → *Re-invite, then try again* opens Servers; **`commands-unregistered`** — a guild with `commands: null` in routed mode → *"<name>: commands were never registered"* → *Try again* (or *Restart*, per decision 4); **`webhook-broken`** — every `routing.webhooks` entry with `broken` → *"#<channel> in <server>: its webhook stopped working (<broken>)"* → *Add it again* opens Servers; **`home-missing`** — `homeGuildId` set and not among `guilds` → *"The home server (<id>) is not one the bot is in, so every plugin nobody has placed is registered nowhere"* → *Set the home server* opens Settings; **`outdated-files`** — each of `status.outdatedFiles` → *"<file> is out of date on this instance"* → *Re-run ops/install.sh* (`go: "none"`; the banner already says it). Empty → the one calm line *"Nothing needs attention."* Rendered by `renderNeedsAttention()`, called at the end of `loadStatus`, `reloadConfig` (after `renderEnvFields`) and `loadRouting` (after `refreshRoutingSteps`), reading the page's current state — the list is derived, never stored. Never a duplicate of the banner's wording beyond the file name.
6. **Pickers, not pasted ids, for `DISCORD_SERVER_ID`, `ANNOUNCE_CHANNEL_ID`, `RELEASE_ANNOUNCE_CHANNEL_ID`.** `FIELD_META` gains `control: "server"` / `control: "channel"` on those three (the hints rewritten: the server one is *"The home server: where a plugin nobody has placed lives and registers its commands. Blank registers those commands globally (can take about an hour to appear)."*; the two channel hints keep their meaning and lose nothing). `buildEnvControl`'s new branch builds an `rb-select` from the pure `pickerOptions(key, discovery, value)` → `[{ value, label, group? }]`: for `server`, `""` as *— none: register globally —* then every guild by name; for `channel`, `""` as *— default —* (the label the existing select uses) then every text channel of every guild, grouped by server (`<optgroup label="<server>">`), labelled `#<name>` with ` · the bot can't post here` when `!canSend`; a stored value that matches no option is kept as its own option `<id> (not visible to the bot)`, exactly as the existing select branch keeps an out-of-enum value. The branch returns through the common tail, so `data-key` and `id` are the same as before and the bar reads the same key and value the id field wrote. **Degrades to the plain id field** when `routingData.discovery` is null or stale (`isDiscoveryStale`) at render time; `refreshEnvPickers()` (called from `loadRouting` after `refreshRoutingSteps`) upgrades a plain field to the picker in place once discovery is ready, carrying the control's current value across (an in-progress edit survives) — never the other way.
7. **Nothing here touches the Apply bar's contract**: a picker is a `[data-key]` control like any other; the Servers tab has no `[data-key]`, `data-plugin`, `data-setting-key` or `data-secret-key` control at all, and `onControlEdited` returns early for `.servers` (the tab's root section class) right after its `.route` return, so a webhook paste never refreshes the bar. A webhook URL is never written to `localStorage`/`sessionStorage`, never put in an attribute, never in a message.

## Deviations from the plan

- **The implementation branch was normal-merged with current `origin/main` @ `a754487` before final verification.** That brings in #300 Part A / PR #303's vendored `@rackbops/styles` 0.2.42 and removal of the local switch override. The merge was automatic; this PR keeps #246's scope and does not edit the generated theme stylesheet.
- **Server-card and Needs-attention wording is this session's own choice, not a byte-for-byte reproduction of decision 3's illustrative quotes.** Decision 3 gives example sentences (`"music — anywhere · posts to #spotify (webhook)"`, `"wow — #general, #raids · posts as the bot"`) but, unlike #245's `placementSummary` (which named the function and pinned its five exact sentences in the coverage table), names no function for these and pins no exact string in Step 3's test table — the pinned parts are `serverCardModel`'s data fields (`commands.state`, `scope`, `postsTo`, `webhook`, `byDefault`), all implemented and tested exactly as specified. `pluginPlacementText` (index.html) renders reasonable prose consistent with the examples' intent: `"posts to #<ch> (webhook)"` / `"(webhook stopped working)"` / `"posts to #<ch> as the bot"` when there's no active webhook for that channel.
- **`retryRegistration`/`addWebhook`/`removeWebhook`/`refreshDiscoveryAll` track busy/settled state through a new `serverActionState` Map** (`{ busy, message }` per subject key: `add:<guildId>`, `remove:<channelId>`, `retry`, `discovery`), the same shape and reason as #245's `routeState` — read fresh at every `renderServers()` call rather than closed over a DOM node a rebuild might have replaced. Not named in the plan (which only names `pollForResult`), but directly implied by review lens A's own named focus on "the poller under a failed read / a 401 / a supersede."
